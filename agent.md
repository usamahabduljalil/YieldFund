## What we are building

YieldFund on NEAR is community fundraising through eligible yield donations. Supporters allocate a token to a campaign vault; realized eligible surplus supports a fixed Sputnik DAO treasury; that DAO governs community payments. Supporters retain a redeemable claim on recoverable capital, which can lose value and be delayed. A deposit gives no DAO voting power.

Original hackathon P0: one fictional open-source campaign, one allowlisted test token, one Rust vault, one strategy and one DAO. Its public lifecycle is complete. The user expanded scope to permissionless multiple campaigns, verification by DAO approval, mainnet support, real Rhea/Trezu integration, GitHub publication and Vercel hosting. Follow [the expansion plan](docs/EXPANSION_PLAN.md) for this new work; do not infer completion from the original milestone.

The funded simulator remains the demonstrated baseline. Mainnet Rhea/Trezu lifecycle implementation is now requested but remains incomplete. Never describe simulation or read-only protocol discovery as live yield integration. Reuse Sputnik governance; verification is approved by a configured DAO, not directly by campaign creators or individual council members.

## Engineering rules

- Recommended frontend: React + TypeScript + Vite, shared tokens and typed NEAR client; pin versions after validation.
- Evaluate HOT Connect against actual testnet requirements. Do not assume a historical Wallet Selector package/version is the current best integration.
- Rust `near-sdk` vault with internal registry, ledger, operation journal and typed strategy adapter. The vault owns the lending position.
- Use raw integer token units, checked arithmetic and string JSON amounts. No floating-point money arithmetic.
- Accepted deposits create nominal units as idle capital. Lending allocation is a separate operation.
- Fully redeem and reconcile before priced withdrawals/distributions; no outstanding in-transit assets or unresolved valuation.
- Healthy settled deposits only; block deposits and donations during impairment.
- At settlement: `A = C + V + T - X`, `B = min(A,P)`, `Y = max(A-P,0)`. Withdraw `b` units for `floor(b * min(A,P) / P)`; handle final-claim dust explicitly.
- Donations cannot reduce backing below outstanding nominal claims. Verify surplus provenance; quarantine unsolicited transfers.
- Reserve cash/units before outgoing calls. Private stage-specific callbacks validate operation IDs and versions. Roll back confirmed failures once; unknown outcomes require reconciliation, never blind retries.
- Authenticate the exact token predecessor in `ft_on_transfer`; rejected hooks return unused tokens through the resolver, with no manual double refund.
- Financial fields become immutable once deposits begin. No arbitrary target, asset sweep, caller-supplied valuation or administrative force-success.
- Contract state and finalized receipts are authoritative. Wallet approval, broadcast hashes and DAO approval alone are not completed payments.
- Simulator profit/loss changes actual test-token backing. Test controls must be absent from production builds.
- Document deployment keys and upgrade authority; a retained full-access key can replace code despite contract restrictions.
